# Polisnab module drafting

Точка входа для черчения 2D-планов модулей Полиснаба через MCP-сервер
`autocad-mcp` (инструмент `mcp__autocad-mcp__polisnab`, бэкенд file_ipc → живой
AutoCAD 2027). Детали живут в двух файлах — этот SKILL их не дублирует:

- **`CLAUDE.md`** (корень репо) — грабли и правила (FILEDIA, сериализация
  координат, forward slashes, `ok:true`≠успех, правила расстановки мебели,
  пристенные элементы, `wall_side` offset). **Перечитывай перед нетривиальной
  ручной сборкой.**
- **`PROJECT-BRIEF-autocad-mcp-polisnab.md`** — полный план, стандарт слоёв,
  dimstyle, реальные размеры компонентов, статус фаз.

## 0. Проверка окружения (ДО первого черчения)

Не начинать, пока не подтверждено:

1. **MCP подключён.** Инструменты `mcp__autocad-mcp__*` доступны. Если нет —
   `/mcp reconnect`. Реконект обязателен после **любой** правки Python (даже
   одной константы).
2. **AutoCAD виден и развёрнут** на весь экран. Свёрнутое/перекрытое окно →
   `get_screenshot` вернёт чёрный кадр. Если кадр чёрный при видимом окне —
   попросить пользователя выполнить `REGENALL` в командной строке AutoCAD.
3. **Диспетчер перезагружен для ЭТОГО чертежа.** LISP-диспетчер
   (`lisp-code/mcp_dispatch.lsp`) живёт в namespace конкретного документа.
   Открыли новый чертёж → диспетчер потерян → `APPLOAD` или
   `(load ".../mcp_dispatch.lsp")` в этом документе. Симптом потери: команды
   молча не срабатывают.

Быстрая проверка состояния без скриншота: `drawing info` / `get_variables`.
Скриншоты большие и жгут контекст — снимать, только когда действительно нужно
*увидеть* геометрию (см. CLAUDE.md § Screenshots).

## 1. Что использовать: шаблон или ручная сборка

Два готовых генератора Phase 4 (`operation` инструмента `polisnab`) собирают
всю сцену — стандарты + оболочку + проёмы + мебель — одним вызовом на **пустом**
чертеже. Всегда предпочитай их ручной сборке, когда запрос ложится на шаблон.

### `generate_dormitory_room` — общежитие / вахтовый модуль
Раскладка стен (актуальна с 2026-07-24): **вход — ЗАПАДНАЯ стена** (короткая),
окно — ВОСТОЧНАЯ (короткая), **локеры — ДВА блока по 2 ячейки в ЗАПАДНЫХ углах**
(SW = южная стена у зап. торца, NW = северная стена у зап. торца, оба у стены с
дверью, вне рядов кроватей), пара(ы) односпальных кроватей у восточной стены,
разделённых зазором (не перегородкой). Кровать single теперь **825×2000** (не
900×2000). N/S — длинные стены (6000), W/E — короткие (2400): окно на короткой
стене, не на длинной. (Реф. `reference-4bed-room-layout.png` рисовал дверь-юг и
локеры-запад одним рядом — БОЛЬШЕ НЕ ТАК.)

- **Кровати примыкают ВПЛОТНУЮ к длинным стенам (0 мм).** Раньше ряды
  ЦЕНТРИРОВались по высоте (`y_margin`) → виден зазор до стены; это была не
  «старая ширина 900», а независимая, не проверявшаяся логика центрирования
  (уменьшение 900→825 даже увеличило зазор). Фикс: `sy=iy0+w/2`, `ny=iy1-w/2`;
  центральный проход = `inner_h - 2*w = 450` мм авто.
- **Локеры-на-юге одним рядом (пред. версия) НАКЛАДЫВАЛИСЬ на южные кровати** —
  южный ряд кроватей сам стоит фронтом к южной длинной стене. Решение: два
  коротких блока в свободных ЗАПАДНЫХ углах (у двери), вне зоны кроватей.

**Автопроверка пересечений (2026-07-24):** после сборки оба генератора считают
AABB каждого элемента и проверяют все пары. Любое пересечение → `verified=false`
+ в `warnings` список пар с величиной нахлёста в мм (`collision: 'A' <-> 'B'
overlap NxM mm`). Касание встык (0) не считается. Т.е. `verified` теперь = «сцена
без коллизий по геометрии», а не «кто-то посмотрел глазами». `bed_pairs=2` на
6000×2400 проходит проверку (`verified=true`, warnings пусто) — подтверждено и
оффлайн-тестом, и вживую.

`data`: `length_mm` (=6000), `width_mm` (=2400), `series` (="arctic"),
`bed_pairs` (=1), `origin_x` (=0), `origin_y` (=0). `bed_pairs`, не влезающие по
длине, тихо опускаются с warning (`bed_pair N omitted`); это не коллизия,
`verified` остаётся по факту пересечений. Про origin — см. § 1b.

### `generate_studio_module` — студия-модуль
Референс `reference-studio-module-layout.png`, сжатый в 6000x2400. Дверь + окно
+ двуспальная кровать + тумба + стол + стул + шкаф + изолированный санузел (душ +
унитаз + раковина за реальной дверью) + конвектор + щиток.

`data`: `length_mm` (=6000), `width_mm` (=2400), `series` (="arctic"),
`origin_x` (=0), `origin_y` (=0) — см. § 1b.
- **Никогда не помечен verified live** — эта плотная комбинация всегда
  возвращается `verified=false`. Подтверждать скриншотом перед сдачей.

`series` определяет толщину стены: `arctic` = 150 мм, `standard` = 75 мм.
Оба генератора возвращают per-step ok/error, `entities`, `verified`, `warnings`.
**`verified=false` = геометрию ещё не смотрели глазами** — проверь скриншот
перед тем как доверять.

### Когда собирать из примитивов
Ручная сборка (`draw_module_outline` → `insert_interior_wall` → двери/окна →
мебель по отдельным `insert_*`), когда:
- планировка не совпадает ни с одним из двух референсов (другой набор зон,
  тамбур/гардероб, нестандартное деление);
- нужен размер вне 6000x2400 с иной раскладкой, чем просто масштабированный
  шаблон;
- пользователь диктует конкретную расстановку узел за узлом.

При ручной сборке действует весь свод правил из CLAUDE.md — особенно:
- **пристенные элементы** (конвектор/сплит/щиток/душ/тумба/шкаф) — только у
  стены, тыльной гранью к внутренней грани, центр на `depth_mm/2` от неё;
- **`rotation_deg=0` у разных генераторов = РАЗНЫЕ стены** (toilet/sink → +Y
  север; convector/split/panel/nightstand/wardrobe → −Y юг; shower — угловой
  −X/−Y). Проверять по докстрингу каждого;
- **между мебелью не ставить `insert_interior_wall`** — читается как несущая
  стена; кровати рядом разделяются **зазором**;
- **`wall_side` offset отсчитывается от ВНЕШНЕГО угла** — ряд у стены начинать
  от внутренней грани (`offset=t`), ширину ячейки ужимать под чистый пролёт
  (`W-2t`), иначе крайние ячейки тонут в торцах;
- **`erase_window` прибит к слоям стен** (`AR-WALL`/`AR-WALL-INSUL`) — мебель им
  не стереть; для мебели `entity list <layer>` → `entity erase` по хэндлам.

## 1a. Работа с референс-чертежом заказчика

Заказчик присылает картинку плана (иногда с ТЗ, иногда без). Наша задача —
**воспроизвести замысел через нашу модульную систему**, а не срисовать чертёж
пиксель-в-пиксель. Порядок чтения:

**Шаг 1. Калибруй масштаб по подписанной размерной линии.** На чертеже почти
всегда есть хотя бы одна подписанная размерная линия (напр. `5900`). У неё две
роли: (а) **линейка** — по ней меряешь в мм всё, что НЕ подписано (см. Шаг 3);
(б) сама подписанная цифра — это, как правило, **заданный габарит**, к которому
и строим (см. Шаг 3, случай 2), а не просто вспомогательный масштаб. Если
размеров нет вовсе — меряй от известного узла (дверь, кровать) обратным ходом.
Пиксельный обмер НЕподписанных деталей ненадёжен (см. § 4 и
`[[reference-pixel-runs-not-crops]]`) — используй линейку только чтобы отличить
«примерно 6 м» от «примерно 9 м», а не чтобы вытащить точную цифру там, где её
не подписали.

**Шаг 2. Читай ПЛАНИРОВКУ (это и есть замысел, его берём с чертежа):**
- сколько спальных мест и как стоят кровати (ряды, пары, к какой стене головой);
- где вход, где окно, где локеры/мебель/санузел;
- какие зоны отделены перегородкой, а какие просто зазором.
Это — то, что заказчик действительно сообщает чертежом.

**Шаг 3. Различай ТРИ вещи — намерение, НЕподписанные детали, подписанные
цифры. Это разные правила, не сваливай в одно:**

- **намерение** (расстановка узлов: что где стоит) → всегда бери с чертежа.

- **случай 1 — детали БЕЗ подписанного размера** (ширина двери/окна нарисована
  «на глаз», толщина линии стены, габарит пиктограммы кровати/локера) → НЕ мерь
  их по картинке, подставляй НАШ проверенный стандарт (PROJECT-BRIEF § 7): вход.
  дверь 950, межкомн. 840, окна 925/1120, кровать 900×2000 / 1200×2000,
  локер-ячейка ~600×420, душ 800/900. Пример: дверь на чертеже шириной «на глаз»
  → игнорируй ширину, ставь 950.

- **случай 2 — габариты, ЯВНО ПОДПИСАННЫЕ ЦИФРОЙ** на чертеже/в ТЗ (напр.
  `5900`, `2438`) → это, как правило, ОСОЗНАННО заданный размер (реальный
  ISO-контейнер, требование ТЗ), а не «на глаз». **По умолчанию строй ИМЕННО под
  эти цифры**, а НЕ подгоняй к ближайшему нашему каталожному (6000×2400).
  Подгонять к каталогу можно ТОЛЬКО если пользователь явно попросил «приведи к
  нашему стандартному/каталожному размеру» — иначе тихо изменишь габарит здания,
  который заказчик задал намеренно. Если подписанная цифра не ложится на
  генератор напрямую — это довод в пользу ручной сборки, а не молчаливой
  подгонки.

- **серия (arctic 150 / standard 75)** — это ТЕПЛОТЕХНИЧЕСКАЯ спецификация, а не
  планировка; по картинке плана она надёжно не читается. Берётся из ТЗ; без ТЗ —
  дефолт (обычно arctic) с явной пометкой «предположение».

> Прогон 2026-07-24 (референс `reference-4bed-room-layout.png`, БЕЗ реального ТЗ,
> картинка как условный пример) намеренно строился под 6000×2400, а не под
> подписанные 5900×2438 — это был тест логики чтения, а не исполнение реального
> заказа. На РЕАЛЬНОМ чертеже с ТЗ по правилу выше строили бы под 5900×2438.

**Шаг 4. Сопоставь с генератором.** Если планировка ложится на референс
`generate_dormitory_room` (вход-запад / окно-восток / локеры-юг / пары кроватей)
или `generate_studio_module`, вызывай шаблон с выведенными параметрами
(габариты — по Шагу 3: подписанные цифры как есть, иначе наш каталожный дефолт;
плюс `bed_pairs`/`series`). Если не ложится — ручная сборка (§ 1). Затем — верификация скриншотом (§ 3), сравнение с оригиналом
**по смыслу планировки**, не пиксель-в-пиксель.

## 1b. Многокомнатные комплексы: `origin_x` / `origin_y`

**Снято 2026-07-24.** Оба композита принимают `origin_x` / `origin_y` (дефолт
`0,0` — прежнее поведение байт-в-байт). Это мировые координаты ВНЕШНЕГО
юго-западного угла модуля; сдвигается ВСЯ сцена — оболочка, проёмы, мебель,
санузел, MEP и подписи ВХОД/ОКНО/ЛОКЕРЫ. `setup_dimstyle` геометрию не рисует
(только переменные DIMSTYLE), сдвигать там нечего.

Несколько комнат ставятся на ОДИН чертёж повторными вызовами с разными origin:

```
generate_dormitory_room(..., origin_x=0,    origin_y=0)
generate_dormitory_room(..., origin_x=6300, origin_y=0)   # 300 мм зазор
```

Как это устроено (важно, если правишь генераторы): всё абсолютное считается от
`ix0/iy0/ix1/iy1`, которые теперь мировые (`ox+t`, `oy+t`, `ox+L-t`, `oy+W-t`).
Пока новая координата пишется через них — origin проезжает сам собой.

**Ловушка, на которой уже поймали баг:** `offset_mm` у `insert_exterior_door` /
`insert_window` / `insert_locker_row` — это смещение ВДОЛЬ СТЕНЫ от её угла, а НЕ
мировая X/Y; генератор сам добавляет `module_origin` внутри. В
`generate_studio_module` `door_center`/`win_center` держатся абсолютными (от них
пляшут конвектор и щиток), поэтому в вызовы проёмов идёт `door_center - ox`.
Передать туда мировую X = **двойной сдвиг**: при origin=0 это незаметно, вылезет
только на сдвинутой комнате.

**Комнаты между собой: передавай `scene`.** Автопроверка внутри вызова видит
только элементы СВОЕЙ комнаты — `_Compose` живёт один вызов. Чтобы новая комната
проверилась против уже нарисованных, отдай их payload'ы в `scene`:

```
a = generate_dormitory_room(..., origin_x=0)
b = generate_dormitory_room(..., origin_x=6300, scene=[a.payload])   # b видит a
```

Каждый результат возвращает `boxes` / `labels` / `swings` (мировые AABB) именно
для такой сцепки, плюс `bbox` / `outer` — габарит комнаты. Чужие элементы в
warning'ах помечаются источником: `[room@0,0] insert_bed[1S]`.

Глобального реестра сцены НЕТ намеренно: он протухает в тот момент, когда
чертёж чистят, и начинает выдавать призрачные коллизии по стёртой геометрии.

## 1c. Три семейства проверок

Проверок теперь три, и они живут по РАЗНЫМ правилам — не смешивать:

| что | правило | категория warning |
|---|---|---|
| `boxes` — физическая геометрия | не пересекается с другой физической геометрией | `collision` |
| `labels` — подписи MTEXT | не пересекается ни с чем (нечитаемо = дефект), но **дверь не блокирует** | `collision` |
| `swings` — зона распашки двери | требование ЗАЗОРА, а не объект: блокируется физикой, свободно проходит над подписями, сама препятствием не является | `door_swing_collision` |

Любое срабатывание роняет `verified` в `false`.

**Распашка проверяется и ВНУТРИ одной комнаты.** Дверь, открывающаяся на кровать
или локер, — та же физическая ошибка, что дверь в соседний модуль: полотно не
проходит. Никакой границы «своя мебель / чужая мебель» нет, проверка одна.

Из зоны распашки namеренно исключены:
- **подписи** — текст не препятствие. Иначе тег `ВХОД`, который `_label_opening`
  специально ставит за стеной (ровно туда, куда выметает наружная дверь), давал
  бы ложное срабатывание в КАЖДОЙ комнате;
- **своя оболочка** (`draw_module_outline`) — её bbox это весь прямоугольник
  модуля, любая внутренняя дверь «попадала» бы в него тривиально.

Зона распашки = AABB СЕКТОРА (петля + дуга), считается через тот же `_arc_points`,
которым дуга рисуется, — предсказание и геометрия не могут разойтись.

Ширина подписи ОЦЕНОЧНАЯ: `0.7 × высота` на символ, привязка MC (диспетчер рисует
`_J _MC`, точка вставки = ЦЕНТР текста). Метрик шрифта через file_ipc нет. Оценка
намеренно ЗАВЫШЕНА: слишком широкая рамка покажет почти-касание как коллизию
(человек отбросит), слишком узкая — молча пропустит реальный нахлёст.

**Тест 2026-07-24 (две комнаты, зазор 300) теперь падает автоматически** —
`verified=false`, без разглядывания скриншота. Ловится и распашка, и подписи:

```
door_swing_collision: 'insert_exterior_door' swing is blocked by
    '[room@0,0] insert_bed[1S]' - overlap 450x250 mm
    '[room@0,0] insert_bed[1N]' - overlap 450x250 mm
collision: 'insert_exterior_door:label[ВХОД]' <-> '[room@0,0] insert_window:label[ОКНО]'
    overlap 220x150 mm
```

То есть полотно не просто задевает габарит соседа — оно выметает 450×250 мм
ПО ОБЕИМ кроватям комнаты A. На `origin_x=8000` та же пара проходит чисто.

**Проверка говорит ЧТО не так, но не чинит.** Практические выводы:
- зазор между модулями со стороны двери — **≥950 мм** (радиус распашки), либо
  разворачивай вход на другую стену. 300 мм не хватает;
- подписи разносить по высоте или гасить (`label=None`) на смежных стенах: теги
  `ОКНО` левой комнаты и `ВХОД` правой встают на одной высоте (`y≈1200`) и
  налезают друг на друга — на скриншоте это читается как «ВХОДКНО».

Ограничения проверки, о которых стоит помнить:
- всё считается по AABB, а не по реальному контуру. Для повёрнутой мебели и для
  сектора двери рамка ЗАВЫШЕНА — возможны «почти-касания», помеченные как
  коллизия. Смотри величину нахлёста в мм: 5×5 это округление, 450×250 — нет;
- ширина подписи оценочная (см. выше), так что нахлёст подписей — сигнал
  «проверь глазами», а не точный обмер.

Следующий шаг поверх этого — сборка многокомнатных комплексов (несколько комнат
в одном здании с общими стенами).

## 1d. Коридорная схема (Phase 4b, шаг 1)

**Дверь в ОБЩИЙ коридор открывается ВНУТРЬ комнаты.** Наружу она перекрывает
проход и мешает соседним дверям. Это ПРОТИВОПОЛОЖНО дефолту свободностоящего
модуля, где `"out"` правильно — там полотно выходит на улицу.

Минимальный рабочий вызов (обе комнаты вдоль одной стороны коридора):

```
cor = insert_corridor(origin_x=0, origin_y=0, length_mm=12000, width_mm=2500)
a = generate_dormitory_room(..., origin_x=0,    origin_y=2500,
                            door_wall="S", door_swing="in", window_wall="N",
                            scene=[cor.payload])
b = generate_dormitory_room(..., origin_x=6000, origin_y=2500,   # стык на x=6000
                            door_wall="S", door_swing="in", window_wall="N",
                            scene=[cor.payload, a.payload])
```

(Стену на стыке в таком виде рисуют ОБЕ комнаты — 300 мм в двух полосах.
Как сделать её одной — § 1f.)

**Окно ОБЯЗАНО переехать с E на N.** В ряду комнат вдоль коридора E/W — это
МЕЖКВАРТИРНЫЕ стены, коридорная — S, наружная только N. Окно на E не просто
«смотрит не туда»: его тег `ОКНО` рисуется на 250 мм за стеной, то есть
физически внутри соседней комнаты (проверка ловит: нахлёст 420×150 мм).

**Что стало параметризуемым** (дефолты прежние, старые вызовы не изменились):
`door_wall` (="W"), `door_swing` (="out"), `door_offset_mm` (=None → по центру
стены), `window_wall` (="E"), `window_offset_mm` (=None). Локеры и кровати
по-прежнему прибиты — это следующий шаг, если понадобится.

Центрированная дверь на S ложится в просвет между локерами SW (кончаются на
x=1350) и южной кроватью (начинается с x=3800): сектор `x [2525,3475]`. Это
УТВЕРЖДЕНО тестом, а не совпадение — при смене мебели проверка среагирует.

### `insert_corridor` — сегмент коридора

`data`: `origin_x`, `origin_y` (юго-западный угол ПРОСВЕТА), `length_mm`,
`width_mm` (=2500, ЧИСТАЯ ширина), `label`, `series`/`wall_thickness_mm`,
`wall_south` (=true), `wall_north` (=false). Только вдоль +X; коридор С-Ю пока
не поддержан.

**Стены — настоящие толстые стены** (двойная линия + серая заливка утеплителя,
`AR-WALL`/`AR-WALL-INSUL`), та же конструкция, что у `draw_module_outline` и
`insert_interior_wall`. До 2026-07-24 это были линии нулевой толщины, и коридор
читался как подпись в пустоте.

**Правило одной строкой: сторона, к которой примыкают комнаты, стены НЕ
получает.** У комнаты уже есть своя стена на y 2500..2650 — ровно там, где
встала бы стена коридора; получились бы две полосы встык = двойная стена. В
реальном здании стена комнаты И ЕСТЬ стена коридора. Отсюда три конфигурации:

| схема | `wall_south` | `wall_north` |
|---|---|---|
| комнаты только с севера (шаг 1) | `true` | `false` |
| комнаты только с юга | `false` | `true` |
| двусторонняя, комнаты с обеих (шаг 2) | `false` | `false` |

В двустороннем случае `boxes` пустой — коридор не владеет ни одной стеной,
только подписью и зоной `clearances`. Это не вырожденный случай, а норма.

**Толщина — по серии (arctic 150), НЕ 75 как у `insert_interior_wall`.**
Обоснование: пока эта стена существует, она НАРУЖНАЯ стена комплекса и требует
утеплённой оболочки. Внутренней перегородкой она не станет никогда — при
зеркалировании второй ряд комнат приносит свои стены, и коридорная тут просто
не рисуется (`wall_south=false`). То есть она либо наружная, либо её нет.

**`width_mm` — ЧИСТАЯ ширина** (то, что важно для эвакуации); полосы стен
рисуются СНАРУЖИ неё (южная занимает y [−t, 0]). Поэтому добавление стен не
меняет зону `clearances` ни на миллиметр — расчётный слой не затронут.

**2500 мм — РАСЧЁТНЫЙ дефолт, а не подтверждённый норматив.** Столько нужно на
разойтись вдвоём плюс полотна дверей, и арифметика двусторонней схемы сходится
ровно. По СП/ГОСТ на ширину эвакуационных путей НЕ сверялось — сверить до
любой реальной сдачи.

**Торцы намеренно ОТКРЫТЫ.** Глухая стена в торце читается как тупик, а коридор
обязан заканчиваться выходом, лестницей или продолжением — чем именно, пока не
известно. На чертеже, предмет которого пути движения, глухая стена поперёк
эвакуационного пути хуже незакрытого края: первое дезинформирует, второе честно
незавершено. Добавить потом тривиально.

**Просвет проверяется отдельно от стен.** Полосы стен зарегистрированы как
`boxes` (у них появилась реальная толщина — они полноправные препятствия), но
главное для коридора — что ПРОСВЕТ между ними свободен. `insert_corridor`
публикует `clearances` — зону, обязанную оставаться пустой. Это четвёртое
семейство проверок (§ 1c):

| | нарушается | игнорирует |
|---|---|---|
| `clearances` — просвет коридора | физикой **и** распашкой двери | подписи |

Подписи проход не блокируют намеренно: тег `ВХОД` коридорной двери по
построению рисуется в коридоре — нормальная практика черчения, не препятствие.

`swing="out"` на коридор теперь **падает автоматически**:
```
clearance_blocked: 'insert_corridor:passage' is obstructed by
    'insert_exterior_door' - intrusion 950x950 mm
```

## 1e. Двусторонний коридор — южный ряд (Phase 4b, шаг 2)

Зеркальный ряд по другую сторону коридора: дверь на СЕВЕРНОЙ стене, окно на юге.

```
cor = insert_corridor(origin_x=0, origin_y=0, length_mm=12000, width_mm=2500,
                      wall_south=False, wall_north=False)   # комнаты с обеих
ny, sy = corridor_row_origins(corridor_origin_y=0, corridor_width_mm=2500,
                              room_width_mm=2400)           # → (2500, -2400)
n = generate_dormitory_room(..., origin_y=ny,
                            door_wall="S", door_swing="in", window_wall="N", ...)
s = generate_dormitory_room(..., origin_y=sy,
                            door_wall="N", door_swing="in", window_wall="S",
                            scene=[cor.payload, n.payload])
```

**`origin_y` считается несимметрично — это и есть главная ловушка шага.**
`origin_y` — ЮГО-западный угол комнаты, поэтому:

- северный ряд: `origin_y = cy + ШИРИНА_КОРИДОРА` (комната начинается там, где
  коридор кончается);
- южный ряд: `origin_y = cy − ШИРИНА_КОМНАТЫ` (комната кончается там, где
  коридор начинается).

Одно слагаемое — ширина коридора, другое — ширина КОМНАТЫ. Считать «минус
ширина коридора» — типовая ошибка: комната наедет на проход. Хелпер
`corridor_row_origins()` возвращает обе координаты сразу, пользоваться им.

**Мебель менять НЕ надо, но не потому, что она «привязана к W/E».** Локеры
стоят на S и N стенах (два ряда, у западного торца), кровати прижаты к
внутренним граням S и N. То есть мебель как раз на тех стенах, которые меняются
местами. Работает это потому, что раскладка СИММЕТРИЧНА относительно оси
запад–восток: пара локеров и пара кроватей зеркальны сами себе. При
несимметричной мебели (одна кровать, шкаф только у севера) южный ряд
пришлось бы разворачивать явно.

**Геометрическая проверка НЕ валидирует ширину коридора.** При `swing="in"`
полотна обоих рядов остаются внутри своих комнат и в просвет не заходят
вообще — коридор шириной 1000 мм пройдёт проверку так же чисто, как 2500.
2500 — величина про человеческий поток (разойтись вдвоём), а не про AABB;
подтверждать её по СП/ГОСТ, а не тестом.

**Известно-хорошее:** коридор 12000×2500 без стен + по 2 комнаты с каждой
стороны на `origin_x` 0 и 6000, `origin_y` 2500 / −2400 — все четыре
`verified: true`, ноль warnings, живьём в AutoCAD. Секторы распашки:
северный ряд `y [2650, 3600]`, южный `y [−1100, −150]` — просвет `y [0, 2500]`
чист с запасом. Коридор длиннее 6000 собирается СЕГМЕНТАМИ встык
(`origin_x` 0 и 6000): торцы открыты, зоны `clearances` смыкаются в один прогон.

## 1f. Общая стена между соседями в ряду (Phase 4b, шаг 3)

**Граница между двумя комнатами рисуется ОДИН раз — той комнатой, что западнее.**
То же правило, что уже сформулировано для `insert_corridor` («сторона, к которой
прижаты комнаты, стены не получает»), только применённое вдоль ряда. До шага 3
две соседние комнаты рисовали каждая свой торец, и стык выходил 300 мм — две
150-мм утеплённые оболочки лицом к лицу между двумя ОТАПЛИВАЕМЫМИ помещениями.

```
n = 2                                  # комнат в ряду
for i in range(n):
    r = generate_dormitory_room(..., origin_x=6000*i, origin_y=ny,
                                door_wall="S", door_swing="in", window_wall="N",
                                **room_row_walls(i, n),      # ← правило ряда
                                scene=list(scene))
```

`wall_west` / `wall_east` принимают три значения:

| значение  | что рисуется                                    | когда           |
|-----------|-------------------------------------------------|-----------------|
| `True`    | полная утеплённая оболочка (`series`, 150/75)   | реальный торец  |
| `"party"` | ОБЩАЯ стена с соседом, `party_wall_thickness_mm`| есть сосед вост.|
| `False`   | не рисуется вообще — стена соседа               | есть сосед зап. |

Правило ряда (его отдаёт `room_row_walls(i, n)`, руками не писать —
off-by-one тут молчаливый): комната 0 → `{True, "party"}`, средние →
`{False, "party"}`, последняя → `{False, True}`; одна комната → обе `True`.

**ШАГ РАССТАНОВКИ НЕ МЕНЯЕТСЯ** — комнаты по-прежнему встык, `origin_x = L*i`,
здание из n комнат ровно `n*L`. Меняется только полоса ВНУТРИ габарита: у
комнаты 0 восточная стена 100 мм вместо 150, а комната 1 не рисует западную
вовсе, и её интерьер начинается прямо на своей габаритной грани. Между
интерьерами — ровно 100 мм.

**Толщина общей стены = 100 мм (`PARTY_WALL_THICKNESS`), не 150 и не 75.**
Рассуждение, а не вкус:
- по обе стороны ОТАПЛИВАЕМЫЕ комнаты, так что работа, ради которой существует
  150-мм арктическая оболочка (утепление против −50 °C снаружи), тут не нужна
  вообще: это утепление между +20 и +20;
- но это и не 75-мм перегородка `insert_interior_wall` — та отделяет санузел
  ВНУТРИ одного жилья, где акустически разделять некого. Здесь — граница между
  спальнями РАЗНЫХ жильцов, то есть акустика + противопожарный отсек;
- 100 мм — типовая межкомнатная сэндвич/каркасная панель модульных зданий и
  следующий типоразмер в ряду 50/80/100/150/200.

**Не подтверждено:** СП 51.13330 требует Rw ≥ 50 дБ между комнатами разных
жилых ячеек; 100-мм панель под это НЕ проверялась. Статус тот же, что у
`CORRIDOR_WIDTH=2500` — инженерный дефолт, а не норма. Поэтому это **параметр**
(`party_wall_thickness_mm`), а не константа в коде: поднять можно без правки.

**Торцы W/E были свободны — и это надо было проверить, а не предположить.** В
коридорной схеме дверь на S, окно на N, локеры на S и N. Но два элемента
ПРИВЯЗАНЫ к торцевым граням: ряд локеров стартует от западной внутренней грани,
а изголовья кроватей стоят в 50 мм от восточной. Обе привязки пережили правку
только потому, что вся расстановка написана через `ix0`/`ix1`, а те стали
считаться по-сторонне (`ox + side_t["W"]`, `ox + L − side_t["E"]`). Численно
они сдвинулись — у средних комнат ряда интерьер шире.

**Новая проверка `open_side` — она обязана была приехать вместе с фичей.** Все
остальные семейства спрашивают «что-то мешает?». Эта спрашивает обратное: если
комната НЕ нарисовала стену, потому что ею владеет сосед, — сосед её правда
нарисовал? Без неё `wall_west=False` на ПЕРВОЙ комнате ряда (ошибка на единицу)
оставляет модуль открытым наружу, и все прежние проверки проходят чисто:
ничего не пересекается, ничего не заблокировано, стены просто нет.

Проверяется по `wall_bands` (полосы, реально нарисованные соседями), а НЕ по их
`bbox`: габарит комнаты покрывает стык и в том случае, когда сосед пропустил ту
же самую стену — обе комнаты кивают друг на друга, а стены нет ни одной.
Полоса поиска берётся СНАРУЖИ габарита (при нулевой толщине внутренняя грань и
есть габаритная, стена соседа лежит за ней) и по ЧИСТОЙ высоте `iy0..iy1` —
иначе продольные стены соседа задевают её углами и «покрывают» стык.

**Проём в ненарисованной стене — жёсткая ошибка (`ok:false`), не warning.**
Резать 950-мм дыру в стене, которой нет, — это пара косяковых линий в воздухе.
Проём на стене `"party"` — warning + `verified=false`: построить можно, но окно
смотрит в комнату соседа, а `insert_exterior_door` рисует ВХОДНУЮ дверь.

**Ловушка, на которой это чуть не уехало в прод:** дверь/окно СТИРАЮТ и
ПЕРЕРИСОВЫВАЮТ всю свою сторону стены целиком. Значит резчику надо отдать те же
пофасадные толщины, с которыми рисовался контур, иначе продольная стена
возвращается с отступом 150 мм в углу, где сосед 100 мм (или его нет) — тихий
дефект ровно там, где стоит дверь. Тест `test_door_redraw_keeps_the_mixed_corners`.

**Известно-хорошее (живьём, 2026-07-27):** коридор 12000×2500 без стен + по 2
комнаты с каждой стороны, `origin_x` 0 и 6000 — все четыре `verified: true`,
ноль warnings. Первая комната ряда: `side_thickness` `{S:150, N:150, W:150,
E:100}`, полоса `E` = `[5900, 6000]`. Вторая: `{S:150, N:150, W:0, E:150}`,
западной полосы в `wall_bands` нет вообще (контур 9 примитивов вместо 12).
На стыке одна полоса, визуально тоньше соседней 150-мм продольной стены.

### 1f-bis. Party-wall у studio (2026-07-27)

Тот же идиом, что у dormitory: `wall_west`/`wall_east` (True/`"party"`/False),
`party_wall_thickness_mm`, `room_row_walls(i, n)` — хелпер общий на оба
генератора. Толщина та же, 100 мм, обоснование не меняется.

**Разница — в том, что тянут за собой сдвинувшиеся грани.** Раскладка studio
АСИММЕТРИЧНА, и это ровно то, что dormitory скрыл:

| группа | привязка | что в ней |
|---|---|---|
| западная | `ix0` | вход, окно, кровать, шкаф, щиток |
| восточная | `ix1` (через `san_x`) | санузел, душ, раковина, унитаз, стол, стул |

При `wall_east="party"` восточная грань уезжает на 50 мм, при `wall_west=False`
западная — на 150 мм. Санузел сохраняет свои 1100 мм (san_x едет вместе с ix1),
разницу забирает жилая зона. В dormitory это прошло незаметно только потому, что
там раскладка зеркально симметрична относительно оси З–В.

**Почему это безопасно:** флаги никогда не делают стену ТОЛЩЕ оболочки
(150 → 100 → 0), поэтому чистый интерьер только растёт. Передадите
`party_wall_thickness_mm` больше 150 — узнаете об этом от проверки на
пересечения, а не от чертежа.

**`door_swing` параметризован, `door_wall`/`window_wall` — НЕТ, намеренно.** У
dormitory стороны свободно менялись N↔S, потому что мебель зеркальна. Здесь вся
раскладка построена вокруг «вход на юге, окно на севере» (конвектор под окном,
щиток у двери, кровать головой на север). Поменять их местами — это зеркалить
раскладку, а не добавить флаг. Практическое следствие: **studio обслуживает
коридор ТОЛЬКО с юга.** Северный ряд из studio сейчас собрать нельзя, это
отдельная задача.

## 1g. Номер помещения (2026-07-27)

`room_number` — необязательный параметр ОБОИХ composite-генераторов. Номер
**передаётся, а не выводится**: какой это по счёту номер, знает сборщик здания,
а не генератор комнаты. По умолчанию номера нет вообще.

**Место — центр чистого интерьера** (`_room_number_position`). Обоснование, а не
вкус; два альтернативных варианта отклонены:
- **у входа** — двусмысленно ровно там, где это важно: в коридорной схеме двери
  соседних комнат стоят на одной стене в нескольких метрах, и номер у косяка
  читается как принадлежащий коридору или соседу с той же лёгкостью, что и своей
  комнате;
- **в свободном углу** — однозначно, но произвольно, и переезжает при любой
  правке мебели.

Центр — это ещё и то место, где в обеих раскладках есть пол: тег попадает в
проход между рядами кроватей (dormitory) и между шкафом и столом (studio).

**Для произвольной раскладки свобода центра НЕ гарантирована — и это специально
не утверждение, а проверка.** Номер идёт на слой TEXT тем же стилем/высотой
(`LABEL_HEIGHT`), что ВХОД/ОКНО/ЛОКЕРЫ, и попадает в семейство `labels`: не
физическая геометрия (в payload нет `bbox`), поэтому дверь он не блокирует, но
наложение на мебель или другой тег репортится как `collision`.

## 1h. Торцы коридора (2026-07-27)

**Дефолт НЕ изменился — торцы по-прежнему не рисуются.** Рассуждение шага 1
осталось верным: глухая стена поперёк эвакуационного пути дезинформирует, пока
неизвестно, что там дальше. Изменилось то, что теперь это можно ЗАЯВИТЬ, когда
известно.

`end_west` / `end_east`, три состояния:

| значение | что рисуется | когда |
|---|---|---|
| `None`/`False` | ничего (дефолт) | коридор продолжается / планировка не решена |
| `"wall"` | глухая полоса поперёк | реально закрытый торец |
| `"door"` | та же полоса с проёмом `end_door_width_mm` + полотно | торец с выходом |

Полоса лежит СНАРУЖИ чистой длины (как боковые стены — снаружи чистой ширины),
поэтому прямоугольник прохода и зона `clearances` не меняются от того,
нарисованы торцы или нет.

**Полотно навешено на НАРУЖНУЮ грань и открывается ОТ коридора** — дверь на пути
эвакуации открывается по ходу движения. Следствие: сектор не заходит в проход.
Развернёте внутрь — проверка `clearance_blocked` сработает (закрыто тестом
`test_inward_leaf_would_block_the_passage`, это не везение геометрии).

**Что видит проверка:** полосы торца публикуются в `boxes` (препятствие) и в
`wall_bands` (доказательство для `open_side` — комната, упёртая в торец, может
не рисовать свою стену); распашка — в `swings`; дыра — в `openings`.

**Оба торца `"wall"` без двери → warning** «nobody can leave it». Единственный
случай, когда генератор скажет что-то вместо того, чтобы молча нарисовать
заказанное.

**Известно-хорошее (живьём, 2026-07-28).** Все три узла подтверждены в AutoCAD:
- номер: dormitory 6000×2400, `room_number="101"` → `verified: true`, ноль
  warnings, тег в центре (`[2842.5, 1125]..[3157.5, 1275]`), в проходе между
  локерами и кроватями;
- торцы: коридор 6000×2500 со стенами S+N, `end_west="wall"`,
  `end_east="door"` → полоса `end[W] [-150,-150]..[0,2650]`, две полосы
  `end[E1/E2]` с проёмом 950 по центру прохода, свинг `[6150..7100]` целиком
  снаружи;
- studio-ряд: 201 (`E=100`) + 202 (`W=0`, западной полосы в `wall_bands` нет),
  оба без collision/swing/clearance/open_side, номера 201 и 202 на месте.

## 1i. Полнота мебели — отдельное семейство проверок (2026-07-28)

**Коллизионные проверки польстят пустой комнате.** Комната, тихо потерявшая обе
пары кроватей из-за нехватки места, возвращала `verified: true` — сталкиваться
стало нечему. Добавлено семейство `incomplete:`, которое спрашивает не «что-то
мешает?», а «то, что заказали, вообще построено?».

Любая недостача → `verified=false` + warning с **числом и причиной**:

```
incomplete: beds - 3 of 4 placed (S row 1/2, N row 2/2; a 2000 mm bed needs
that much clear frontage and the door swing, the lockers and the end walls
take the rest)
```

Причина едет вместе с числом намеренно: «3 из 4» говорит, что что-то не так;
причина говорит, **двигать дверь, убирать кровать или поворачивать комнату** — а
это и есть решение, которое принимает вызывающий. В payload добавлены
`beds_placed` / `beds_requested`.

У studio счётчика нет, но есть **фиксированный ростер**: проверяется, что все 14
элементов дошли до списка боксов. Ловит суб-генератор, вернувший `ok:true` и не
нарисовавший ничего — не нарисованный унитаз ни с чем не столкнётся.

## 3. Верификация — `ok:true` не есть успех

`drawing save` / `save_as_dxf` / `plot_pdf` эхом возвращают путь без проверки
записи. Всегда проверять артефакт на диске (или `DWGTITLED`/`DWGNAME`).
Пути — только forward slashes (`C:/...`). После генерации, помеченной
`verified=false`, — скриншот перед сдачей результата.

## 4. Мелкие декоративные значки

Глифы (дверные символы, иконки мебели) НЕ сходятся через несколько раундов
текстово-координатного описания. Если значок не тот после **2–3 попыток** —
прекратить описывать прозой; либо (а) дать агенту свободу дизайна в заданных
границах, либо (б) дать **референс-изображение** для попиксельного анализа
(Python + PIL). Зумленный кроп — это всё ещё «на глаз» (стоило 3 неверных
раковин): дампить прогоны тёмных пикселей по строкам и сверять заявленный размер
с измеренной фичой, чтобы найти реальный масштаб.

**Параметризуй то, что будут подбирать на глаз.** Величина, которую явно будут
крутить (угол створки, длина панели, размер глифа) → сразу в аргумент
генератора: тогда следующая примерка = одна вставка и ноль реконектов.
